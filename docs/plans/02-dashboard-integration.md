# Hermes Dashboard Integration and Streaming Architecture

The source baseline is `~/dev/hermes-agent` at `c419cf7c86`. Compare against the Dashboard network module of mobile `91d9b43` and llmwiki's "Hermes Dashboard backend contract". The paths and methods below come from source-code inspection; the deployment version, permissions, plugins, route switches, and proxy compatibility are verified by M0b on the designated real service `192.168.2.171:9119`. ## Process and Transport

| Layer | Responsibilities |
| --- | --- |
| Main | BrowserWindow, system login, credential storage, Dashboard address validation, authentication refresh, ticket broker, file and microphone permissions, Utility Process lifecycle. Uses Electron `session.fetch` / `net` for REST requests, authorization exchange, and response streams |
| Dashboard Utility Process | One logical connection context per connected Dashboard; chat JSON-RPC uses a persistent connection, and Kanban opens a separate WS per opened board. Handles WS frame validation, RPC correlation, event normalization, state reducer, session replay, backpressure, connection state, and bounded data caches |
| Renderer + preload | Local pages; a narrow typed bridge exposes concrete commands such as `connect`, `listBots`, `openChat`, `send`, `stop`, `answerRequest`, `subscribe`. REST caches use paginated DTOs. The standalone computer window obtains only a short-lived display ticket through a controlled bridge and handles RFB with noVNC; React rendering of message bodies and computer frames are scheduled separately |

The Utility Process requests a scoped ticket for the current connection through Main and uses it against the connection generation. Verify the WS client against the target deployment's system proxy, PAC, WSS certificates, reverse-proxy prefix, and reconnect behavior. Node's WebSocket library has its own network stack, so proxy rules are adapted and tested separately. If it cannot meet deployment requirements, move socket I/O into a dedicated Electron sandbox transport renderer so Chromium handles the network, while the Utility Process continues to project and aggregate. The computer stream is never converted to JSON/Base64 through the main chat pipeline. [Electron net](https://www.electronjs.org/docs/latest/api/net) · [Electron MessagePorts](https://www.electronjs.org/docs/latest/tutorial/message-ports)

A single window builds subscription ports with `MessageChannelMain`; the data port only sends redacted domain events. Main/service command receivers validate sender, schema, window, account, and scope; preload exposes only the allowed narrow interface, and the renderer receives only the necessary DTOs. On window close, sign-out, connection switch, or process crash, close the ports and retire old generations. In production, enable context isolation, sandbox, and strict CSP, disable nodeIntegration, and reject unexpected navigation and new windows. Chat Markdown disables raw HTML; copying code and opening links use explicit actions; attachment previews and external links follow allowed protocols and origins. The main process never exposes arbitrary fetch, file paths, or raw IPC. [Electron security guide](https://www.electronjs.org/docs/latest/tutorial/security)

Authentication adapts to the deployment shape. A gate-protected Dashboard uses the native bearer for REST and exchanges one-time WS tickets; chat and Kanban tickets are obtained separately, and tickets are re-signed when expired or already used. The source also has a loopback session-token path; M0b must pin down its credential entry and WS handshake, and tokens provided by the user are managed independently. Production defaults to HTTPS/WSS; exact loopback may use HTTP/WS. M0b records the actual scheme of the designated test service; if it only provides HTTP/WS, configure a test exception for the exact origin `192.168.2.171:9119` only — do not extend it to arbitrary intranet addresses, ignore certificate errors, or replace OAuth. Persist credentials that must survive in Keychain or Electron safeStorage; prefer keeping access tokens in memory only; credentials, tickets, request bodies, and screen contents never enter logs. Refresh single-flight per connection; after a 401 retry only safely replayable reads, and handle writes per their idempotency and read-back rules. Bind reverse-proxy prefixes to the connection and restrict request and redirect origins.

### New Bot Configuration Through First Reply

Creation uses `mirror_credentials:false`, so it does not copy credentials for the user or inherit usable models. M2 owns the configuration state machine for the same profile, and M3's model page reuses it:

1. Query the profile's model options, current selection, and authorization state from the backend. M0b pins the real endpoints, fields, and permissions; an identity already logged into the Dashboard does not mean the model is authorized.
2. Credentials remain managed by the backend. Open the same Dashboard's configuration page bound to the original profile, and re-read state after returning to the app; a browser completion page alone does not prove success. If the deployment cannot locate or configure that profile, go to M0c to fix it, and never make the user guess the page or hand-edit files.
3. After saving provider/model, re-read the same profile. Handle unauthorized, model unavailable, timeout, and partial configuration success separately, preserving the slug, draft, and completed steps; callbacks from an old account or profile are invalid.
4. Enable the first send after configuration is verified, with canonical claim followed by real inference. New-Bot acceptance passes only after a reply is received and persistent history is read back; restarting continues the same session. Extra paid probes are triggered by explicit test actions, never by automatically calling the model on every state check.

### Session Consistency and Recovery

1. Data keys at minimum contain `connectionId + verifiedPrincipal + profile + storedId`. Runtime ids, request ids, and seq additionally bind `connectionGeneration` and the replay epoch. Canonical hints in the roster may paint a preview first; before sending, run the exact title query and owner validation. When the compacted tip changes, merge into the original Bot.
2. Existing sessions are resumed directly. Create before the first send only when the exact query succeeds and the session is confirmed missing; the client single-flights per profile, and retries of the same creation reuse the idempotency key. In the current source, an ordinary create returns a lazy session; an explicit `session.title {session_id,title:"Bot Chat"}` attempts to persist and checks for conflicts in the title transaction. Claim the title first, then read back with the exact query, and only send to the candidate after confirming that the same-profile hidden canonical record matches the candidate stored id. On 4022, re-query and resume the winning canonical, drop the candidate, keep the draft, and let the user confirm sending again. On pending, a visible same-name old session, or uncertain ownership, keep the draft and state the reason. M0b reproduces the title race with two clients sending the first message simultaneously, observing the candidate empty row and subsequent recovery. Enable first send for newly created Bots only after persistent read-back and conflict protection are verified on the target deployment. If protection is missing, the existing Bot Chat path may continue, and claim capability goes to M0c; M2 and first-version acceptance stay blocked until the designated deployment re-verifies.
3. Accept out-of-order WS events and RPC responses. Generate a client operation id before sending, and maintain "to send / awaiting confirmation / queued / replying / completed / stopped / failed". Reconcile with the admission/message ids actually provided by the target version; for unconfirmed writes check history and active state first, and auto-retry only when there is reliable server idempotency. Keep the draft while running by default and offer "Stop"; enable explicit queueing only after deployment verification. Avoid applying a late termination event from an old turn to the next turn.
4. On disconnect, mark recovery first, then exchange tickets with exponential backoff plus jitter. Wait for gateway ready, resume with the stored id to obtain the current runtime id, persistent history, inflight, and open requests, and replay by same-epoch `last_seen`. Buffer live events until the baseline is established, deduplicating by scope, seq, and turn/row id. If replay is truncated, the epoch changes, the process restarts, or the runtime id becomes invalid, rebuild from a new snapshot and persistent history. If still active after recovery, keep Stop and settle with a termination event or re-verified server state.
5. M0b actually tests two Dashboard clients opening the same running Bot Chat at the same time. In the current source the live resume path tries to add the caller as an active session subscriber, and the submit path has separate transport rebinding. Use two clients to prove that observation keeps receiving deltas and that closing the observer does not interrupt the current turn, and verify write permission and approval behavior on both ends. When needed, use persistent history and active snapshots for a read-only display; allow sending, approval, and stop only after control ownership is confirmed. Switching Bots, closing details, or refreshing details should preserve active replies and pending requests.

### Pending Requests and File Delivery

- The Utility Process maintains a pending index isolated by account, profile, session, and request id; subscription/reconciliation is not trimmed by the selected Bot or the visible list. M0b verifies request discovery for unopened Bots, cross-end handled receipts, and recovery, with M0c filling gaps. Reconnect verifies open requests before restoring actions; notification dedupe and read positions persist, and switching accounts invalidates immediately.
- Files are handled by Main using system open/save dialogs; the renderer only holds opaque handles bound to window, account, profile, and purpose. Uploads restrict type/size; cancel and failure preserve drafts; the renderer is forbidden from submitting arbitrary local paths. Remote references are validated for ownership and validity before sending.
- Downloads re-verify resource identity and permission; short-lived authorization expiry can be re-signed; never directly trust URLs or paths in messages. Large files stream to a temporary file and are atomically placed on success; there is progress, cancel, retry on failure, and overwrite confirmation. Previews use restricted local content and never execute HTML/scripts; external opening accepts only files the user explicitly selected and that finished downloading.
- The index covers full history pagination and compaction continuation, deduplicated by stable resource identifiers. Deleted, inaccessible, and temporarily failed are distinguished; a library item can link back to its source message. Real acceptance includes an uploaded file being read by the model, and generated artifacts still saving and opening after reconnect and restart.

### Local Data and Upgrade

Main single-writes versioned JSON under the app's `userData`, serializing temporary-file writes and atomic replacement; credentials are stored separately in Keychain/safeStorage. Persistent data includes connections, account-isolated drafts/attachment metadata, section pins, unread positions, window and language/appearance preferences, and pending operation ids; authoritative history and leases are always restored from the server. Staged attachments have size/expiry limits; when the original file is unavailable, the user must re-select it.

Input is saved with a short debounce and flushed before switching Bots, closing the window, and a normal quit. Crash recovery reads the latest complete version; pending sends reconcile first and are never auto-resent. Back up before each schema migration; on failure keep the original file and provide a recovery entry; older versions refuse to write a higher schema. Sign-out clears credentials, ports, and in-memory projections while keeping account drafts isolated; only an explicit user clear deletes that account's local data, backups, and staged attachments.

The first version uses a signed installer with manual in-place upgrades, offering download and release notes on the About page, with auto-update deferred. M5 upgrades from the previous beta of this rebuild, covering normal migration, force quit, and migration-failure recovery; rollback first restores the matching data backup, and old versions must not overwrite the new format. Keep a stable app id and data directory; importing old Desktop data is out of scope for the first version.

### Computer Viewing and Takeover

The computer tab appears only on deployments where the `display.status` capability is confirmed. Opening the tab is read-only; after an explicit "Wake", wait for authoritative state and rate-limit thumbnail fetches. When someone else takes over or the server returns suppressed, clear the preview immediately, and never use old frames to fake a live screen. When opening the standalone window, first call `display.observe {profile}`, establish a read-only RFB connection with a one-time ticket, and bind the server-returned viewer id and profile. The ticket is separated from the chat authentication channel and must not enter the clipboard or logs.

After the user clicks take control, call the deployment-verified lease claim and verify the returned holder/epoch/viewer hash. In the current source, acquire can replace another viewer's lease, so read-then-acquire is racy. For non-preemptive takeover, treat server-side conditional claim or verified equivalent protection as the enabling condition; without the capability, read-only viewing is only an intermediate deliverable, and M0c must add atomic conditional claim and verify it on the designated deployment — M4 must not be closed. Forward input only when the lease matches and the viewer connection is healthy. On return, release key and mouse state, then call release with the current viewer id and wait for the receipt to return to view-only. On leaving, disconnect, or lease loss, cut input immediately; on reconnect, observe first and allow explicit takeover only after re-checking permission. Closing the window returns the current window's lease on a best-effort basis; avoid force release after losing the viewer id. Test "takeover response later than close" and "two ends contending, reclaiming, reconnecting" separately against the real service. Remote shutdown and returning control are offered separately.

M0c's conditional-claim contract must validate holder and expected epoch within the same server transaction/lock before writing; conflicts return the authoritative lease without changing the current holder. Retries by the same viewer are idempotent; a caller that lost viewer identity cannot release someone else's lease. Field and method names are frozen by the protocol owner; do not disguise designed conditional parameters as current APIs. Re-verify: two viewers claiming concurrently with only one succeeding; late responses/window close; disconnects and lease reclaim; user-initiated takeover and forced preemption must be distinguished, and the first version offers no force-takeover entry.

## High Throughput and Backpressure

- The Utility Process parses, validates, and aggregates. Text deltas are merged per session and turn within 16–32 ms before emitting `StreamBatch`, with per-batch frame and byte limits. Server requests and terminal states are delivered with priority. Merging changes only the batching granularity and preserves text and control-event order within the same turn.
- MessagePort uses an ACK-based bounded window, starting from 8 batches and 512 KiB per subscription as tuning starting points. Slow consumers merge transient progress first and replace backlog projections with snapshots. Raw bodies and must-deliver events stay in bounded logical state and are filled in through server replay or snapshots. Overflow immediately enters a sync-recovery state and is counted.
- Separate persistent REST pagination, active messages, and Bot summaries. Re-render only messages that change; parse Markdown incrementally while streaming and fully render on the terminal state; measure code highlighting and large-file handling before moving them to a Worker. Fix the history page size and retain completed messages within bounds; keep current active replies first, evict inactive pages when the cache exceeds limits, and preserve scroll positioning.
- Verified chat, Kanban, and computer are all WS. If SSE routes appear later, add an incremental parser in the stream service supporting UTF-8 across chunks, CRLF, multi-line `data`, event limits, and AbortSignal. Send Last-Event-ID only when the server declares resumability. The same projection and backpressure strategy applies, and no new SSE proxy layer is required.
- Use traces to measure network read, JSON parse, message copy, Markdown, layout, and RFB stages first. If a CPU hot spot is confirmed to be parsing or transcoding and consistently over budget, first isolate that stage from the shared queue, then compare a Worker or a native Rust module against the same fixture. The native version must show measured gains and pass signing, crash recovery, and install checks for the corresponding architecture. [Electron performance guide](https://www.electronjs.org/docs/latest/tutorial/performance)

### Initial Performance Thresholds

The packaged build is measured on an Apple Silicon reference machine, recording model, OS, power state, and Dashboard version. Use an in-process redacted frame replayer with 4 active Bots at 100 small deltas/second each for 10 minutes, plus a 5-second 5x burst, 10,000 history messages in a single session, and a 60-minute mixed reconnect/idle loop. This synthetic load only proves local pipeline performance and does not start a mock server; re-run interaction scenarios during real chat and computer viewing on the designated service. Record p95, heap and RSS curves, maximum queue, and recovery counts.

- Local frame-to-visible-text p95 ≤ 100 ms, with remote model first-token latency recorded separately. Local feedback for send/switch Bot p95 ≤ 100 ms, and scrolling, Chinese input, and right-column toggling stay operable.
- Under stress, message bodies, confirmation requests, and terminal states are complete, and long replies can be replayed after interruption. The same turn has no duplicate body text, and terminal states never stick in working. The queue returns to steady state after a burst, and memory does not keep growing linearly after the 60-minute loop.
- Run performance sampling in the production configuration, recording first paint, connection, first history page, batch rendering, and computer preview separately. Performance targets are implementation thresholds; concrete baselines are filled in from actual M0b/M5 measurements.
