## 一、双客户端并发回答同一审批

`scripts/gui-concurrent-approval.mjs`：A、B 打开同一 Bot Chat，都收到同一真实 `chmod` 审批；
同时点击（A 拒绝、B 允许）。

| 检查                                               | 结果              |
| -------------------------------------------------- | ----------------- |
| 两端都收到同一审批卡                               | ✅                |
| 两端同时回答后都有终态（回执或「已由另一端处理」） | ✅                |
| 危险命令没有重复执行                               | ✅ 仅一次请求记录 |
| 没有残留审批卡                                     | ✅                |

报告：`docs/evidence/tmp/concurrent-approval-2026-11-04T10-34-09-298Z.json`。

**已知限制（API 能力）**：响应帧是无回执的通知，网关不广播“哪一个回答获胜”。并发回答时，
两个窗口可能各自短暂显示自己的回执，随后又可能折成「已由另一端处理」；实测不同时序下两种表现
都出现过。服务端只结算一次、命令不会重复执行，但客户端无法从 API 得知获胜方，因此不能保证两个
窗口显示完全一致。要彻底解决需要服务端在 settle 后广播带答案的 resolution 事件。

## 二、强退后不自动重发

`scripts/gui-force-quit.mjs`：

| 检查                                                       | 结果 |
| ---------------------------------------------------------- | ---- |
| 发送 prompt 后立即 SIGKILL 主进程（模拟崩溃/强制退出）     | ✅   |
| 重启后恢复同一 Bot Chat                                    | ✅   |
| 输入过的 prompt 在会话中只出现 1 次（无自动重发/重复发送） | ✅   |

报告：`docs/evidence/tmp/force-quit-2026-11-04T10-36-20-752Z.json`。

## 结论

- 并发审批不会导致命令重复执行或残留卡片；跨端回执的完全一致性受服务端事件能力限制。
- 强退不会在重启后自动重发已经在途的消息。

## 三、双客户端同时发送不同消息

`scripts/gui-concurrent-send.mjs`（隐藏窗口、同一 Bot Chat，A/B 同时按 Enter）：

| 检查                                      | 结果       |
| ----------------------------------------- | ---------- |
| 两端各自 prompt 只出现一次（不丢/不重复） | ✅ A:1 B:1 |
| 两轮都完成、各自收到回复                  | ✅         |
| 无连接/错误横幅                           | ✅         |

**已知限制（服务端事件）**：网关不向其他客户端广播“用户消息”事件，只广播助手流/工具/提问卡。
因此实时同屏时，另一端的用户气泡不会出现（`A saw B's prompt=false`），需要在重开/重连后由历史
同步补齐。若要求两端实时看到彼此的用户气泡，需要服务端增加 user-message 广播。

报告：`docs/evidence/tmp/concurrent-send-2026-11-04T11-44-03-175Z.json`。
